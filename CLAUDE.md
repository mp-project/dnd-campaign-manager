# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

npm-workspaces monorepo (Node `>=24 <25`, ESM) for a D&D campaign manager:

- `apps/backend` (`@dnd/backend`): Fastify 5 + Zod (`fastify-type-provider-zod`) + Drizzle ORM on PostgreSQL. Almost all real logic lives here.
- `apps/frontend` (`@dnd/frontend`): Vue 3 + Vite + Pinia + Tailwind 4. Being rebuilt from the clickdummy (see Frontend); theme and assets are in place, pages are still scaffolding.
- `packages/i18n` (`@dnd/i18n`): languages, language choice and glossary terms shared by frontend, backend and the admin website (TypeScript source, no build yet; the backend gets a build when it uses it).
- `packages/test-utils`: shared test helpers.
- `tests/e2e`: Playwright smoke tests (root `playwright.config.ts`).

## Roadmap

The refactoring and module plan (local only, gitignored; backend + frontend per module, domain events with `@EventHandler`, realtime channel, frontend built from the clickdummy) is `docs/plan/refactoring-und-modulplan.md`. Read it before starting work on a new module or on cross-cutting backend/frontend structure, and tick off finished steps there. The clickdummy (`clickdummy/`, gitignored, local only) is the reference for features, flows and theme; admin screens in it are out of scope (separate project).

## Commands

Run from the repo root unless noted.

```bash
npm run dev               # backend (tsx watch) + frontend (vite) together
npm run lint              # eslint over the whole repo
npm run typecheck         # tsc / vue-tsc in every workspace
npm run build
npm run test:unit         # backend jest "unit" project + frontend vitest
npm run test:integration  # backend jest "integration" project (needs test DB, runs in band)
npm run test:integration:docker   # integration tests fully inside compose (profile "test")
npm run test:e2e          # build + playwright
npm run api:types         # regenerate the frontend API types from the backend OpenAPI document
npm run i18n:check --workspace @dnd/frontend   # same keys/placeholders in every language, used keys exist, glossary complete
npm run i18n:types --workspace @dnd/frontend   # regenerate the message key types after changing German messages
```

Single test (Jest, from root):

```bash
npm run test:unit --workspace @dnd/backend -- tests/unit/campaigns.service.test.ts
npm run test:unit --workspace @dnd/backend -- -t "registers module dependencies"
npm run test:integration --workspace @dnd/backend -- tests/integration/campaigns.http.test.ts
```

CI (`.github/workflows/ci.yml`) runs: `lint` → `typecheck` → `api:types` (fails if the generated types changed) → `i18n:check` → `test:unit` → `db:migrate` → `test:integration` → `build`.

### Database

```bash
npm run db:generate       # drizzle-kit generate a migration from schema changes
npm run db:migrate        # apply migrations (drizzle-kit migrate)
npm run db:seed           # bootstrap + ruleset seed data (apps/backend/scripts/seed.ts)
docker compose --profile development up -d db adminer   # local DB + Adminer
docker compose --profile test up -d db-test rustfs-test # integration-test DB on 127.0.0.1:55433, S3 on 127.0.0.1:59000 (both tmpfs)
npm run storage:check --workspace @dnd/backend          # write, read and delete an object with the current env's storage settings
npm run content:reindex --workspace @dnd/backend         # rebuild asset_references by hand (repair); the app does it at startup when needed
```

- Drizzle schema entrypoint is `apps/backend/src/core/db/schema.ts`, which re-exports `src/core/db/schemas/index.ts`. **Each module's table file must be exported from `schemas/index.ts`** or drizzle-kit won't see it.
- Migrations live in `apps/backend/drizzle/migrations` (SQL + `meta/` snapshots, generated). Generated SQL has needed hand fixes before (e.g. enum replacement with dependent indexes/defaults, parenthesized defaults); review it and keep schema, SQL and snapshot consistent.
- Integration tests need `db-test` and `rustfs-test`: `tests/integration/storage.s3.test.ts` and `media.s3.http.test.ts` run against a real S3, each with its own bucket. All other tests use `InMemoryStorage`, which can't show S3 problems.
- Integration tests drop and recreate the `public` and `drizzle` schemas and rerun migrations **before every test** (`tests/setup/integration.ts`). `assertSafeTestDatabaseUrl` refuses to run unless the host is local/`db-test` and the DB name contains `test`. `TEST_DATABASE_URL` defaults to `postgres://postgres:postgres@127.0.0.1:55433/dnd_campaign_manager_test` (`tests/setup/env.ts`).

## Environment

- Three env files: root `.env` (shared compose values), `apps/backend/.env`, `apps/frontend/.env`, each created from its `.env.example`.
- The compose database runs in every profile, so it publishes its port on `127.0.0.1` only and takes its password from `POSTGRES_PASSWORD` in the root `.env` (required, no default; compose builds the containers' `DATABASE_URL` from it).
- `APP_ENV` (development | stage | production) drives compose profile and `NODE_ENV`. Precedence: `COMPOSE_PROFILES` → `APP_ENV` → `production`; `NODE_ENV` → `APP_ENV` → `production`.
- `docker compose --profile development up --build` adds RustFS (S3-compatible storage), Mailpit (SMTP + inbox UI) and Adminer. Caddy is the TLS ingress: `https://api.localhost:8443`, `https://app.localhost:8443`.
- Local dev URLs: API `http://api.localhost:3000/api/v1`, frontend `http://app.localhost:5173/`.
- Web push uses Pusher Beams (optional): the frontend registers through `src/services/pushNotifications.ts` when `VITE_PUSHER_BEAMS_INSTANCE_ID` is set (compose build: `PUSHER_BEAMS_INSTANCE_ID` in the root `.env`). The SDK is a CDN script tag in `index.html`, the service worker is `public/service-worker.js`, which must stay at the site root. The Beams secret key belongs in the backend only.

## Backend architecture

### Import aliases

The backend uses Node subpath imports (`apps/backend/package.json` `imports`): `#core/*` → `src/core/*`, `#src/*` → `src/*`, `#test/*` → `tests/*`. They resolve to `.ts` sources under the `development` condition (set via `NODE_OPTIONS=--conditions=development` in `dev`/`db:seed`) and to `dist/*.js` otherwise. Jest mirrors them via `moduleNameMapper`. Use these aliases instead of relative paths in module code.

### App bootstrap

`src/app.ts` `buildApp()` builds the Fastify instance with Zod validator/serializer, creates the `AppContainer` (`src/core/app/container.ts`), registers core plugins (security, JWT auth, request context, campaign context, authorization, error handler, OpenAPI, health routes) and then mounts all modules under `API_BASE_PATH = /api/v1`. `buildApp` accepts overrides for `env`, `pool`, `modules` and `publicPorts`, which is how tests inject fakes (`tests/helpers/buildTestApp.ts`).

### Module system

- Modules are `AppModule` objects `{ name, dependencies, register(app, container) }` (`src/core/app/moduleSystem.ts`). They are listed in `src/modules/index.ts` (`defaultAppModules`) and registered in topologically sorted order; duplicates, missing deps and cycles throw `AppModuleRegistrationError`.
- Each module's wiring lives in `src/modules/<name>/Setup.ts` and is re-exported from its `index.ts`. `Setup.ts` manually constructs repository → service → use cases → controllers, then mounts routes with `app.register(...)`. Route files use full paths, so `Setup.ts` sets no prefix.
- **Cross-module access goes through the container's dependency registry**, not direct imports of another module's internals: a module publishes `container.dependencies.set(<MODULE>_MODULE_DEPENDENCIES, {...})` (a string token plus exported type), and dependents read it with `container.dependencies.get/require`. The dependency must also be declared in `dependencies` so it registers first. `tests/unit/*.moduleDependencies.test.ts` covers this per module.
- Shared infrastructure is exposed as **ports** on `container.ports`: `permissionService`, `campaignFactPort`, `storagePort` (local / S3 / in-memory; `npm run storage:check --workspace @dnd/backend` verifies it), `emailPort` (SMTP / noop). Modules may wrap ports (e.g. campaigns fills in `campaignFactPort.resolveCampaignAccess`).

### Module layout and request flow

Typical module folders: `domain/dto` (Zod schemas), `domain/entities` (Drizzle tables), `domain/repository`, `service/`, `useCase/`, `http/controller`, `http/routes/v1`, `permissions/`, optionally `email/`. There is no `config/` folder: permission keys live only in `permissions/` (a named object like `ASSETS_PERMISSIONS`, accessed by name), paths are inline in the routes file and `security` is a constant there.

Flow: route (Zod `schema` + `config.permission`) → controller (extends `AbstractController`, wraps work in `this.execute(...)`, which maps `ZodError` → `ValidationError` and unknown errors → `InternalError`) → use case (one class per operation, `execute(context, ...)`) → service (holds `db`, `transactionManager`, repository) → repository (Drizzle queries, takes the db/tx handle as first arg). Each operation has its own use case and controller (`handle`). The controller only parses input and passes the result on; the use case decides what the user gets and returns the response DTO. Mapping functions (`to<Entity>Response`) live next to the schema in `domain/dto/Response<Entity>Dto.ts`. The service holds only shared logic and exposes `db`, `transactionManager` and `repository` publicly. In `auth`, use cases return the session next to the response DTO because controllers set the token cookies (`http/AuthHttpSupport.ts`); the sub-services under `auth/service` keep the domain logic.

Code structure rules (backend and frontend):

- Modules are built on CRUD: create, get, list, update, delete/archive, restore; domain commands that don't fit CRUD (`transfer`, `resolve`, `invite` …) are extra operations in the same pattern.
- One file per use case and per controller (`useCase/Create<Entity>UseCase.ts`, `http/controller/Create<Entity>Controller.ts`); no files that bundle several operations.
- DTOs live in their own files under `domain/dto/`: `Base<Entity>Dto.ts`, `Create<Entity>Dto.ts`, `Update<Entity>Dto.ts`, `Request<Entity>Dto.ts` (params/query), `Response<Entity>Dto.ts`; extra operations get their own DTO file.
- Don't duplicate logic where sharing makes sense: shared within a module → its service; across modules → a container port or module dependency injected through constructors in `Setup.ts`; domain-neutral helpers → `src/core`; recurring flows → base classes. Frontend: shared components in `src/components`, shared logic as composables in `src/core`. Extract only when the same logic with the same meaning is needed in at least two places; no abstraction in advance.

DTOs derive from one `domain/dto/Base<Entity>Dto.ts` schema (`<Entity>BaseSchema`) via `pick`/`partial`/`extend`. Response schemas inherit the input rules, so check that stored data can't violate them before deriving a field; a violation becomes a 500 at serialization. Repository writes are named `create`/`update`/`delete` (with a suffix for secondary entities, status changes are `update*`); reads stay `find*`/`list*`/`count*`. There are no `/admin/...` routes: the route checks the permission and the use case picks the view by role. Content responses say which one they are with `view: "FULL" | "PLAYER"`; FULL (everything, including drafts and GM-only fields) goes to the campaign owner, editors and administrators, so it names the projection, not a role. Campaign roles are `OWNER` (the game master), `EDITOR` and `PLAYER` (`CampaignRole`, `campaignRoleOf` in `#core/content/viewer`). Boolean query parameters use `booleanQueryDto`, not `z.coerce.boolean()`, which turns "false" into `true`.

Rate limiting is central (`src/core/http/rateLimit.ts`): every route gets `ROUTE_RATE_LIMIT` (`GET` higher than writes), counted per user (or client IP when anonymous) and route pattern, so routes don't share a budget. Don't add limits per module; only auth routes and routes that send email set `config.rateLimit: SENSITIVE_ROUTE_RATE_LIMIT`, with a higher budget per IP because several users of one session often share a network. Routes that read media set `MEDIA_READ_ROUTE_RATE_LIMIT`, because a gallery asks for many files at once.

Auth attempts are counted on top of that in `auth_attempts` (`AuthAttemptService`): failed logins, refreshes and verification codes, plus every auth email. Limits are per account or token and, much higher, per IP; blocked requests get 429 with `Retry-After`. Attempts must be recorded outside the request transaction, because the thrown error rolls it back.

Trusted devices (`trusted_devices`, `AuthTrustedDeviceService`) are opt-in: a checkbox on login or password reset, or `POST /me/trusted-device` later. A device still needs the password but has its own attempt limit, so attacks on the account can't lock it out. A password reset during a block lifts the block and links the browser automatically. Password changes, resets and logout from all devices remove all devices.

Busy database: the pool sets `connectionTimeoutMillis` and `lock_timeout` (5 s); both timeouts map to `ServiceUnavailableError` (503).

Inside `inTransaction`, only run queries on the `tx` handle. Calling something that uses its own `db` (for example another module's service or use case) needs a second pool connection while the first is held; with a row lock this can block the whole API (`tests/integration/campaign-memberships.concurrency.test.ts`). Do those lookups before opening the transaction.

### Auth, permissions, campaign context

- JWT access tokens carry `sub` (actor id), `systemRole` and `sv` (session version); request context is on `request.requestContext`. A valid signature is not enough: on every request `container.ports.sessionStatePort` (installed by `auth`) loads the user and accepts the token only if the account is ACTIVE and `sv` equals `users.session_version`; the role comes from the database. Raise `session_version` (`AuthRepository.updateSessionVersion`, or in the tracked user change) to end all access tokens at once: logout everywhere, password change/reset and role/status changes do. Without the port no token is accepted. `buildTestApp` provides a fake that trusts the token; pass `realSessionState: true` to test the real check.
- Registration never reveals whether an address has an account: `POST /auth/register` and `.../request-verification` always answer 202 `{status:"accepted"}` (a taken address gets an info mail instead of a code; while unverified, the latest registration sets the password), `.../verify-email` takes email + code and answers every failure with the same 409. The emailed link only verifies and redirects to `/login?verified=1|0`; it never signs in. Verification and confirmation codes travel by email only, never in a response. Email changes go through `POST /me/email-change` (current password if the account has one), stay in `users.pending_email` and only take effect after `POST /me/email-change/confirm` or the emailed link; the old address gets a notice. `PATCH /me` does not take `email`. OAuth never links to an existing account: if the provider's email is already used (password account or another provider), sign-in is refused with `OAUTH_EMAIL_IN_USE`. Invitations match by email only for verified addresses. `GET /users?search=` matches email addresses only for system admins (everybody else: display name and user tag). User input in `ilike` goes through `escapeLike` (`#core/db/escapeLike`). Redirect targets from clients go through `normalizeRedirectPath`, which keeps only same-origin paths.
- Every route under `/api/v1` sets exactly one of `config.permission = { key, hideAsNotFoundForPlayers? }` or `config.public: "<reason>"`; otherwise registration throws at startup (`assertRouteDeclaresAccess`), and `tests/unit/routeAccess.test.ts` lists the public routes. Permission definitions of campaign-scoped keys set `campaignRoles` (`ANY_CAMPAIGN_ROLE`, `CAMPAIGN_EDITOR_ROLES`, `CAMPAIGN_OWNER_ROLE`) and optionally `campaignRoleDenial: "notFound"`; on routes with `:campaignId` the hook checks them before the use case (non-members 404, other roles 403/404, system admins pass). Use cases keep their own checks. The authorization `preValidation` hook (`src/core/http/authorization.ts`) calls `permissionService.require` against `request.campaignContext`, falling back to a `"global"` context. Request context, campaign context and authorization run in `preValidation`, so 401/403 come before schema validation (400); malformed campaign ids are ignored there and left to the schema.
- `request.campaignContext` is resolved from a `:campaignId` route param or an `x-campaign-id` header via `campaignFactPort.resolveCampaignAccess`.
- Adding a permission: define keys + `PermissionDefinition`s (with `campaignRoles` for campaign routes) in the module's `permissions/`, register them in `Setup.ts` (`permissionService.registerDefinitions`), and add keys to the aggregation in `src/modules/auth/permissions/permissions.ts` (`ALL_PERMISSIONS`, `APPLICATION_USER_PERMISSIONS`). System role → permission mapping is in `src/modules/auth/permissions/roles.ts`.
- Linkable content (notes, spells, NPCs, locations, ...) shares its identity in `assets` (`src/modules/assets`). Domain modules don't write `assets` themselves. They call the `AssetsModuleDependencies.service` port (`createBase`, `updateMetadata`, `archiveBase`, `restoreBase`, `assertAvailable`, `resolveVariant`, ...) inside their own transaction and check their own domain permissions. Players only see campaign assets that a registered `AssetVisibilityProvider` (e.g. content shares) grants.
- **Content types register once.** A module that owns an asset type calls `AssetsService.registerContentType` with only what can't be derived elsewhere: `assetType`, `kind` (`RULE`: released per asset; `STORY`: shared, with a required `playerView` and optional `assertShareable`), `editRoutes`, `revertibleActions`, and for checks `references`, `properties`, `verify` and `usesContent`. Release, shares, edit routes, undo rights, the reference index and the end-of-action checks all read it from there; there are no separate `register…` calls per concern. Cross-module extensions of the kernel stay separate: visibility providers (grant sources such as shares or features revealed by a released class), the archive guard of asset-links, the deactivate hook of content-shares and usage providers (shares).
- **Read access is decided in one place**, `ContentAccess` (`assets/service/ContentAccess.ts`). A use case loads it once per request with `AssetsService.access(context, campaignId)` (or `accessFor(viewer, db)` inside a transaction) and asks it by purpose (`ContentReadPurpose` in `#core/content/access`): `READ` for details and the ends of links and usages, `CATALOG` for what the campaign may use, `MANAGE` for the campaign's own content on its management routes. `require(purpose, asset, message)` answers 404 for everything hidden, `readableIds`/`filter` decide for loaded rows, `listWhere(purpose, { scope, status })` gives the same rule as SQL for lists (management lists of the full view leave archived content out unless asked for), `listReadableOwnIds` lists a player's own readable assets. Global lists outside a campaign use `AssetsService.globalListWhere`. Modules never combine status, scope, shares and in-use ids themselves; `tests/integration/content.access.test.ts` checks every role and purpose and that the SQL matches the code.
- Rule content (features, classes, species, and later feats, spells, items, backgrounds …) reaches players differently from story content: global content is always visible if it fits the campaign ruleset; custom content needs a release per asset (`assets.released_to_players`, tracked, campaign assets only), after which every player of the campaign sees and may use it, read-only. Content types of `kind: "RULE"` allow it; assets itself then provides the released active ids as a visibility provider. Rule content is not registered as shareable. Custom features also become visible through a released source that grants them (classes and species register a visibility provider that reads the ids straight from the stored json, so one definition that no longer parses can't break player reads; feats … to follow), and content assigned to a character stays readable after a release is withdrawn (to be added by the character modules). Archived rule content leaves the catalog unless the campaign still uses it: content is in use while non-archived content of a type registered with `usesContent: true` (characters, NPCs; the character modules will register them) refers to it in `asset_references`. The access session counts a use only if the viewer may read the content that uses it, so a player sees the archived class of a character they see, not what a GM-only NPC uses (`tests/helpers/contentUse.ts` stands in for those modules in tests). GMs still manage their own archived content under the campaign routes. Player views leave out hidden choice options entirely (not just their link), so their response schemas use the `*ChoiceViewSchema` without the stored checks.
- Players see story content through shares (`src/modules/content-shares`): a GM reveals one asset to all or to selected active players, until revoked or until `expiresAt`. Global assets fitting the campaign ruleset can be shared as well, to draw attention to them; each campaign has its own share. A share is no content, so it has no history and no soft delete: revoking deletes it, an expired share is hidden at once and deleted before the next list or change (outside the transaction, so a refused request can't roll it back). Only content types of `kind: "STORY"` can be shared, optionally refusing single assets with `assertShareable`. They bring their `playerView` (`schema`, `load`): `GET /campaigns/:campaignId/shares/:shareId/content` resolves a share to the module's player view (editors get it as a preview), and only what the schema describes leaves the server. The client picks its view by `assetType`. Players poll `GET /campaigns/:campaignId/shares?since=` for new shares; there is no push yet.
- Notes (`src/modules/notes`) are the first domain module on assets and the pattern for the following ones: own note id plus `asset_id` (unique active, composite FK to `assets(id, campaign_id)`). The asset holds name, summary, status and tags, the note row the text. Create writes asset, note, tags and `relatedLinks` in one action; updates send `expectedVersion` (note) and `expectedAssetVersion` (asset) and change tags before asset fields, because tags are locked before the asset. DELETE archives the asset and restore brings it back. When shareable content leaves ACTIVE (draft or archive, on every path), content-shares ends its shares through a deactivate hook, and they don't come back. Lists carry no text; it comes with the detail view. GMs and editors write; players only read active notes shared with them, in the player view, which is also the share content. Slugs come from `slugify` in assets (`unique` for names that may repeat). Edit routes are built in batches per asset type (`editRoutes` of the content type).
- Features (`src/modules/features`) are declarative rule definitions (parameters, choices, resources, scaling, activations, effects, supersedes) on assets of type `FEATURE`, global (`/features`, administrators only, rulesets in the body) or custom per campaign (`/campaigns/:campaignId/features`). `/campaigns/:campaignId/catalog/features` lists what a campaign may use: active global features for its ruleset plus its own (for players only released ones). Each graph part is one jsonb column, checked by the Zod schemas plus `validateFeatureDefinition` (unique keys, references between parts, only whitelisted variables such as `level.class`, `param.<key>`, `scale.<key>`, `resource.<key>.max`, expression limits). The rule parts form one history group, and an update fills in unsent parts from the base version, so a concurrent change to any of them is a 412 instead of a mix. Referenced assets (supersede targets, linked options, asset defaults) are checked by the content verification at the end of every action (`verifyContent`: missing/foreign 404, archived, incompatible or cyclic 409) and block archiving through the reference index. `POST .../resolve` binds parameters, choices and scaling for an actor snapshot and computes values without storing anything; results are cached in-process by feature and asset version. `FeaturesService.evaluateEffects` combines several features (stacking modes, upgrade/replace) for source modules. Expression and payload contracts live in `#core/rules`.
- Classes (`src/modules/classes`) follow the features pattern on assets of type `CLASS`: global (`/classes`, administrators only) or custom per campaign (`/campaigns/:campaignId/classes`, GMs and editors; players after a release). `/campaigns/:campaignId/catalog/classes` lists what a campaign may choose; each class also has catalog routes per section (`progression`, `features`, `choices`, `spellcasting`, `proficiencies`, `starting-equipment`, `multiclass`, `usages`). Core traits are columns, the definition (primary abilities, proficiency rules, starting equipment, progression tracks, one level entry per level with feature grants and parameter bindings, choices, spellcasting profile, multiclass requirements) is one jsonb column per part, checked by Zod plus `validateClassDefinition` (exactly one subclass choice at `subclassSelectionLevel`, levels 1..`maximumLevel`, keys and references by key); parts and level settings form one history group. `code` is a free slug: unique per campaign by index, and for global classes unique per ruleset in the service (2014 and 2024 variants share codes). The `SUBCLASS` choice lists no options (only the `[SUBCLASS]` filter): subclasses name their class, and the subclasses module offers them. The content verification checks referenced assets with `AssetsService.collectReferenceIssues` (expected asset types per field, e.g. `FEATURE` options, `ITEM` equipment, `SPELL_LIST`) and bindings against the granted feature's parameters (`FeaturesService.listParameters`). Archived classes stay in the catalog only while the campaign uses them, marked `selectable: false`, and `requireSelectableClass` refuses them (409); in the player view a hidden grant also takes the choices it asks for and the grants those select. The read models for actor progression are in `ClassViews`. The proficiency bonus comes from the ruleset, not the class.
- Subclasses (`src/modules/subclasses`, own module on top of classes through `ClassesModuleDependencies`) are assets of type `SUBCLASS` that name their class (`classId`, set once). Global ones (`/subclasses`, administrators only) belong to global classes; custom ones (`/campaigns/:campaignId/subclasses`) to the campaign's own classes or to global ones (a homebrew subclass of a global fighter). The selection level and the maximum level come from the class and are not stored. Parts are jsonb columns in one history group: `levels` (only levels with grants, class-shaped feature grants; `CLASS_CHOICE` bindings name a choice of the subclass), `progressionTracks`, `choices` (class choices, no `SUBCLASS`), `spellcasting` (own profile incl. `THIRD` casters, only for classes without spellcasting) and `spellGrants` (`ALWAYS_PREPARED`/`ADDED_TO_LIST`). `validateSubclassDefinition` checks the parts, `validateSubclassAgainstClass` the class rules: everything between the selection level and the maximum level, upgrades/replacements only of features the class or the subclass grants by then, spells only with a caster. The content verification (`SubclassesService.verifyContent`) locks the class (`ClassesService.lockForDependent`: asset, then row, shared) and checks the class (scope, archived, active, rulesets: global subclasses within the class's, custom ones for the campaign ruleset), the class rules, references and feature bindings (`ClassesService.collectGrantBindingIssues`). The reference to the class is `dependent`: `verifyDependents` locks each class once and checks only the class rules of its subclasses, so a class change that would break one (selection level, maximum level, spellcasting, rulesets, draft) is a 409 naming them, while their other issues don't block it; active subclasses block archiving the class. Codes are unique per class (global, and per campaign). Catalog: `/campaigns/:campaignId/catalog/classes/:classId/subclasses` (not paged) and `/campaigns/:campaignId/catalog/subclasses/:subclassId` with `progression`, `features`, `choices`, `spellcasting`, `usages` and `POST selection-check` (`validateSelection`: wrong class, class level outside selection level..maximum, assignment already has another subclass, not selectable). Players need to see the class as well. A released subclass makes its custom features, spells and spell list visible while players may choose its class (global, or released). The actor progression stores the chosen subclass per class assignment and uses `SubclassesModuleDependencies.service` (`validateSelection`, `requireSelectableSubclass`, `listReadableForClass`, `definitionFor`) and `SubclassViews`. No content seed.
- Species (`src/modules/species`) follow the classes pattern on assets of type `SPECIES`: global (`/species`, administrators only) or custom per campaign (`/campaigns/:campaignId/species`). Core traits (code, creature type, lifespan mode) are columns; sizes, movement, age and physical profile, text sections, variant groups and feature grants are one jsonb column each, checked by Zod plus `validateSpeciesDefinition` (one default size at most, exactly one positive base WALK speed, lifespan values only with `SPECIES_SPECIFIC`, unique keys). Variants (subraces, lineages) are assets of their own (`SPECIES_VARIANT`, table `species_variants`) in the scope of their species, under `.../species/:speciesId/variants`, with their own history and release; a variant names a group of its species and adds grants that may upgrade or replace features the species grants (no cycles, not before the target's level). Grant keys are unique across the species and all its variants, because a selection names choices by grant key. Active variants keep the species from being archived, and a species change that would no longer fit its variants (group gone, target gone, rulesets narrowed) is a 409. Species and variant writes lock the species row (`SpeciesRepository.lockSpecies`) before they check each other, variant writes take a share lock on the species asset first (same order as a species update: asset, then row), so a species can't be archived under a new variant. Grant checks load the granted features once (`FeaturesService.inspectFeatures`) and share-lock them on writes, so a concurrent feature change or archive waits; a feature whose stored graph no longer parses is reported as an issue. `validate` checks without locks and reports every issue at once. The definition parts and the lifespan mode form one history group, and an update fills in unsent parts from the base version, like classes. Species and variants of rulesets from 2024 on (edition year; neutral global species count) may not grant features whose effects raise or set ability scores (`raisesAbilityScore`: `MODIFIER` or `BASE_VALUE` on `ability.<abbr>`, any case; a constant penalty is no increase); 2014 races model them as grants. Species grants scale by character level, never by class level, so they may not grant features that depend on one (`usesClassLevel`: `CLASS_LEVEL` tracks or `level.class`). The rules also hold when the feature changes later: the references of species grants forbid the feature properties `USES_CLASS_LEVEL` and (2024) `RAISES_ABILITY_SCORE` (`forbids` in `asset_references`), features report what they are with `ContentTypeDefinition.properties` (`FEATURE_PROPERTIES`), and the content kernel refuses a feature change that a non-archived referrer forbids, at the end of every action (undo and restore too). `/campaigns/:campaignId/catalog/species/:speciesId` has `variants`, `features`, `creation-options`, `usages` and `POST resolve`, which checks a selection (size, variants per group, choices of applying grants) and returns the grants at the character level with their status (`APPLIED`, `UPGRADED`, `REPLACED`, `LOCKED`), each feature resolved, and the summed effects; nothing is stored. For players it is a preview without hidden grants (`toPlayerGrants`, the one filter for player views): they are left out before upgrades and replacements apply, and a choice for one is refused like an unknown key. A variant only makes its custom features visible while its species is released too. Reads leave out variants whose stored grants no longer parse, and a species definition that no longer parses answers 409 on reads; `validate` names both. The character modules use `SpeciesModuleDependencies` (`service`, `variants`, `selection`) for the same, with the full view, and pass their transaction handle as `db` to every read inside their transaction.
- Feats (`src/modules/feats`) follow the classes pattern on assets of type `FEAT`: global (`/feats`, administrators only) or custom per campaign (`/campaigns/:campaignId/feats`). Core traits are columns (`category` as a fixed enum `ORIGIN`/`GENERAL`/`FIGHTING_STYLE`/`EPIC_BOON`, `minimumCharacterLevel`, `prerequisiteCheckMode`); prerequisites (one tree of `ALL`/`ANY`/`NOT` nodes and leaves `ABILITY_MIN`, `PROFICIENCY`, `CLASS`, `SPECIES`, `FEAT`, `SPELLCASTING`, `LEVEL`, `CUSTOM`), repeatability (`ONCE`, `LIMITED`, `UNLIMITED`, `DISTINCT_BY_CHOICE` with a choice key), choices and feature grants (`GRANT`/`UPGRADE`/`REPLACE`, bindings `STATIC`/`CONTEXT`/`FEAT_CHOICE`) are one jsonb column each and one history group, checked by Zod plus `validateFeatDefinition`. Categories other than `GENERAL` need rulesets from the 2024 edition on (`featCategoriesFor`; neutral global feats are `GENERAL`). The content verification checks the global code per ruleset, the category, references (prerequisites are indexed as kind `PREREQUISITE`, so usages show `FEAT_PREREQUISITE`), bindings and prerequisite cycles across feats (a feat as its own prerequisite is refused). The catalog (`/campaigns/:campaignId/catalog/feats`, filters `category`, `level`, `repeatable`) has `categories`, per feat `prerequisites`, `choices`, `features`, `usages`, `POST eligibility-check` (actor snapshot plus acquisition context; three-valued: missing facts give `UNKNOWN` with `unknownFacts`) and `POST resolve` (checks the feat's choices, resolves granted features). Player views keep the prerequisite tree but set hidden asset references to null and leave out hidden options and grants. `eligibleForCharacterId` and a character id instead of the snapshot come with the character modules (`FeatsModuleDependencies`: `service`, `selection`).
- Spells (`src/modules/spells`) follow the feats pattern on assets of type `SPELL` and `SPELL_LIST`: global (`/spells`, `/spell-lists`, administrators only) or custom per campaign (`/campaigns/:campaignId/spells`, `/campaigns/:campaignId/spell-lists`). Core traits are flat columns, one per history field (`level` 0..9, `school`, `isRitual`, casting time `castingTimeType`/`castingTimeAmount`/`castingTrigger`, range `rangeType`/`rangeDistance`/`rangeUnit`, duration `durationType`/`durationAmount`/`durationUnit`, `requiresConcentration`, `componentVerbal`/`Somatic`/`Material`); sections, materials, requirements (`FOCUS`/`FREE_HAND`/`SPECIAL`), targets (with areas), choices, scaling tracks (`CHARACTER_LEVEL` or `SLOT_LEVEL`) and effects (`#core/rules` payloads plus `resolution` attack/save, `targetKey`, acyclic `dependsOnEffectKeys`) are one jsonb column each. They and the core fields they depend on form one history group, checked by Zod plus `validateSpellDefinition` (cantrips use no slot and are no rituals, slot scaling not below the spell level, reactions need a trigger, distance/timed fields only with their type, material components with their entries, costly components neither replaceable by a focus nor consumed without a cost, at least a description, section or effect; expressions may use `level.character`, `level.spell`, `slot.level`, `slot.above`, `caster.*`, `proficiencyBonus`, `scale.<key>`). Check constraints repeat the column rules. A list holds its own entries (`spellIds`, indexed as kind `ENTRY`), and a spell may name lists (`spellListIds`, kind `LIST`); in a campaign a list contains both, so a custom spell can join a global list for its campaign only. References block archiving like everywhere (a listed spell, a named list, the list of a class). A released custom list makes its custom spells visible to players. The catalog (`/campaigns/:campaignId/catalog/spells`, filters `level`, `maxLevel`, `school`, `ritual`, `concentration`, `component`, `effect`, `list`, `class` – the list of the class's spellcasting profile) has per spell `effects`, `lists`, `usages` and `POST resolve` (slot, scaling and resolved effects for a caster; reports what the cast would use, spends nothing); `/campaigns/:campaignId/catalog/spell-lists` has detail, `spells` and `usages`. Slots, prepared spells and concentration are actor state: `actor_spell_assignments` and the actor spell routes come with the actor modules, which use `SpellsModuleDependencies.service` (`requireSelectableSpell`, `checkSpellAccess`, `listsOfSpell`) and `resolveSpellCast`. No import route (import-export module).
- Items (`src/modules/items`) follow the spells pattern on assets of type `ITEM`: global (`/items`, administrators only) or custom per campaign (`/campaigns/:campaignId/items`). The category details are typed columns of one `items` row, not tables per category: weapon (`weaponCategory`, `weaponCombatType`, damage dice or fixed damage, `damageType`, `versatileDiceFaces`, `weaponProperties`, range, `masteryProperty`), armor and shields (`armorCategory`, `baseArmorClass` – the bonus for shields –, `dexterityMode` FULL/CAPPED/NONE, `dexterityCap`, Strength requirement, stealth), tools, containers and magic (`magicBonus` for attack/damage or armor class, `rarity`, `magicItemType`, `attunementMode` NONE/OPTIONAL/REQUIRED, `chargesMaximum`, `recharge`, `sentience`). Check constraints allow the columns of a category only on items of that category; the create DTO is a `discriminatedUnion` on `category`, updates are checked on the merged state by `validateItemDefinition` (changing the category means emptying the old fields in the same request). Effects (`#core/rules` payloads such as `MODIFIER ability.str`, `BASE_VALUE ability.str`, `MODIFIER ac`) carry an `activation` (`CARRIED`, `EQUIPPED`, `ATTUNED`, `ON_USE` with `chargeCost`); feature grants (`GRANT`/`UPGRADE`/`REPLACE`, bindings `STATIC`/`CONTEXT`) and spells the item casts (`spells`, indexed as kind `SPELL`, `castAtLevel` not below the spell level) are jsonb parts as well. The details, magic fields and parts form one history group. `POST /campaigns/:campaignId/catalog/items/:itemId/resolve` calculates for an actor snapshot and a state (carried, equipped, attuned, charges) attack ability and bonus, damage dice and bonus, armor class (or a shield's bonus), every effect with whether it is active, the passive totals and the active granted features resolved; nothing is stored. The catalog also has `effects`, `usages`, `instances` and `POST fork` (a custom copy with `forkedFromAssetId`, which is no reference). Instances (`item_instances`, `/campaigns/:campaignId/item-instances`) hold quantity (only stackable items more than one; several stacks of one item are allowed, and every piece of a stack is in the state of the stack), owner (`UNASSIGNED` or a campaign asset: `ACTOR` = character/NPC/monster, `LOCATION`, `QUEST`, `OTHER`), condition, charges, `equipped` and `attuned` (actors only, attunement where the definition allows it, three per actor and one copy of each item, single pieces only; charges are spent on single pieces too, so a stack is split first); the commands `transfer` (a smaller `quantity` splits the stack), `split`, `merge` (only stacks of the same stackable item, owner and state: condition, charges, equipment, attunement, custom name, notes and knowledge; otherwise 409 with `differences`), `adjust-quantity`, `equip`, `attune`, `spend-charge`, `identify` and `resolve` check the version strictly (transfer, split and merge can't be undone, because they create or delete stacks; they are taken back with the opposite command), and the guard of the tracked instance repeats the rules on undo and restore. They read the current definition; an item with instances can't be archived (archive guard). What players know is in `item_instance_knowledge` (per player or, with `userId` null, for all players; `SEEN` shows the appearance without magic, `IDENTIFIED` the player view of the definition, also when it is not released). Changing instances is left to the GM and editors until the character modules let players handle their own items through `ItemsModuleDependencies` (`service`, `instances`).
- Backgrounds (`src/modules/backgrounds`) follow the feats pattern on assets of type `BACKGROUND`: global (`/backgrounds`, administrators only) or custom per campaign (`/campaigns/:campaignId/backgrounds`). Core traits are columns (`code`, `customizationMode` `FIXED`/`RULESET_CUSTOMIZABLE`, `displayOrder`); `sections` (Markdown, `gmOnly` ones never reach players), `abilityRule` (`NONE`, `FIXED` increases, `CHOOSE_2024`: +3 as +2/+1 or +1/+1/+1 over three named abilities), `proficiencyGrants` (`SKILL`/`TOOL`/`LANGUAGE`, `FIXED` or `CHOOSE` n of the options or of any), `featGrants` (`FIXED` feat or `CHOOSE` by category/named feats), `featureGrants` (`GRANT`/`UPGRADE`/`REPLACE`, bindings `STATIC`/`CONTEXT`), `equipmentOptions` (`EQUIPMENT`/`CURRENCY`/`MIXED`, entries with a fixed item or a choice filter by item and tool category) and `promptTables` (personality traits, ideals, bonds, flaws; with a die every result has exactly one option) are one jsonb column each and, with `customizationMode`, one history group, checked by Zod plus `validateBackgroundDefinition` (grant keys unique across proficiency, feat and feature grants). Edition rules (`validateBackgroundEdition`, in the content verification): `CHOOSE_2024` only from 2024 and required there, customization only before 2024, from 2024 on origin feats only; neutral global backgrounds count as every edition. References carry `forbids` (`collectRuleReferences`): tool proficiencies name `TOOL` items, feats fit the grant's categories (2024: `ORIGIN`), granted features don't use class levels and from 2024 on raise no ability scores, items of a choice fit its filter; feats (`FEAT_CATEGORY_*`) and items (`ITEM_CATEGORY_*`, `TOOL_CATEGORY_*`) report these as `properties`, so changing a referenced feat or tool later is a 409 too. A released background makes its custom features, feats, items and bound asset ids visible, and what those feats grant and offer. The player view leaves out a proficiency grant whose options are all hidden (no options would mean "any") and a whole equipment option if one of its entries is hidden. The catalog (`/campaigns/:campaignId/catalog/backgrounds`, filters `customizationMode`, `abilityMode`, `ability`) has sections `abilities`, `proficiencies`, `feats`, `features`, `equipment`, `prompts`, `usages` and `POST resolve`: checks a character's choices (ability allocation, proficiency choices or the 2014 `customization` with two skills, two tools/languages and optionally the features of another background, feat choices, equipment option and item choices, prompt selections, `existingFeatAssetIds`) and returns ability increases, proficiencies (with `proficiencyKey`), feats (with `featId`), resolved features with `sourceAssetId`, items and `walletDelta`, prompts and non-blocking `conflicts` (proficiencies the snapshot already has, a fixed feat the character can't take again); a chosen feat that is taken twice or already owned and not repeatable (`canTakeFeatAgain`) is refused, and `POST feat-options` lists per feat grant only the feats the character may still take; invalid choices are a 409 listing every issue, nothing is stored. The character assignment (`character_background_assignments`, preview/apply/replace/remove under the actor routes) comes with the actor modules through `BackgroundsModuleDependencies` (`service.requireSelectableBackground`, `selection.resolveBackground`). No import route (import-export module).
- Text content is stored as typed and made safe when it is shown, not refused when it is saved. The server renders Markdown (`#core/text/safeMarkdown`) with markdown-it (`html: false`, raw HTML becomes text, script links are dropped) into `contentHtml`. The frontend may insert only such server-rendered HTML, through one `SafeHtml` component that sanitizes it again with DOMPurify; `v-html` is forbidden everywhere else (`vue/no-v-html`). Raw fields such as `content` and `gmNotes` are shown as text only. SQL safety comes from Drizzle's parameterized queries, so text is never escaped for storage.
- Relations between assets live in `asset_links` (`src/modules/asset-links`). Domain modules register their relations (`service.relations.register`), usage providers and edit routes through `AssetLinksModuleDependencies.service` and call `createLink`, `updateLink` and `removeLink` inside their own action. A new relation needs an entry in `VALID_METADATA` in `tests/integration/asset-links.http.test.ts`. An asset can't be archived while a link of a `blocksTargetArchive` relation or non-archived content that refers to it (`asset_references`) points to it; the check runs at the end of every action that archives the asset (undoing and restoring included), on the final state of everything the action changed. Usages show links, provider items (shares, outline) and, as `typedUsages`, the content that refers to the asset from the index: `id` and `assetId` are the referring asset, `type` is `<its type>_<kind>`, `editRoute` comes from the `editRoutes` of the content type (with `campaignId` null for global content). Everything goes through the access session, and only those who may edit get an `editRoute`.
- What stored content refers to lives in `asset_references` (one row per place: source asset, target, path, kind). It is derived: the content kernel replaces the rows of every touched asset at the end of an action from `ContentTypeDefinition.references`, and the app rebuilds it once at startup when the version stored in `system_runtime_state` (`content.reference_index`) is older than `CONTENT_REFERENCE_INDEX_VERSION`; raise that constant when a type changes what it reports as references. `npm run content:reindex` rebuilds it by hand. A reference may be `dependent` (a subclass on its class): when an action changes the target's content, the kernel checks the non-archived sources again at the end of the action, all of one type at once through `ContentTypeDefinition.verifyDependents` (only the rules against the target, so an unrelated issue of a source can't block the change; without it `verify` runs per source). It is not tracked and not the truth; relations people set themselves stay in `asset_links`.
- Uploaded files live in `media_files` (`src/modules/media`). Uploads go in 8 MiB parts through the API (`media_uploads`, `MediaUploadService`): announce the file, `PUT` the parts in any order, complete. A client that lost its connection asks which parts arrived. Size limits apply when announcing, the type check and hash run on completion. A file row only exists once all of that succeeded. A deleted row stays until `objectDeletedAt` is set, and `npm run media:cleanup` (`MediaCleanupService`) repairs the rest, including expired uploads; it needs an external schedule.
- Limits are `MEDIA_DEFAULT_LIMITS` (`media/domain/MediaLimits.ts`): largest file per type and total per campaign, including running uploads. Variants don't count. Another module can replace single values per campaign with `MediaModuleDependencies.quota.registerLimitsProvider`; media itself knows nothing about the reason. They only apply when the storage is S3 (`MediaQuotaService`); production always uses S3.
- Listing files, announcing and completing an upload, aborting it and deleting a file return `storageUsage` (`usedBytes`, `totalBytes`), so the frontend needs no extra request. It is `null` unless the viewer is an administrator or the campaign owner, and without S3. For everybody else, a 413 also has no numbers.
- Content always starts at `GET /campaigns/:campaignId/media/:mediaId/content`, which checks the rights on every request and then redirects to a signed storage link, so the bytes don't pass through the API and range requests work. A revoked right can last until the link ends (at most twice `STORAGE_DOWNLOAD_URL_TTL_SECONDS`). `LocalStorage` and `InMemoryStorage` can't do that (`supportsDirectDownload`), so there the API streams. Links contain `STORAGE_S3_PUBLIC_ENDPOINT`, which must not be the origin of the app.
- Images get WebP variants (`media_variants`, `?variant=thumbnail|display`) from a separate process, `npm run media:worker` (`MediaVariantService`, `sharp`), which `npm run dev` starts too. Until a variant is ready, the original is delivered. The API must not import `sharp`.
- Campaign-scoped updates use optimistic locking (`src/core/db/optimisticLock.ts`, `version` column, `VersionConflictError` → HTTP 412).

### History

Changes to content are recorded per field in the `history` module (`#core/history`, `src/modules/history`). Tracked today: `asset`, `assetLink`, `campaign`, `campaignMembership`, `ruleset`, `tag`, `assetMedia`, `note`, `feature`, `class`, `species`, `speciesVariant`, `feat`, `spell`, `spellList`, `item`, `itemInstance`, `itemInstanceKnowledge`, `subclass`, `background`, `user`. Read through `GET /history/:entityType/:entityId`, undo through `POST /history/events/:eventId/revert`, restore through `POST /history/:entityType/:entityId/versions/:version/restore`.

- **Writing:** use cases that change tracked rows extend `MutationUseCase` (`authorize` returns `authorized()` or `publicAction("reason")`, `perform` does the work; lookups in other modules go in `prepare`, before the transaction) and write only through `scope.create`, `scope.change` and `scope.softDelete`. Use `history.runAction` directly only if work has to follow the commit, such as an email. An ESLint rule forbids direct writes to tracked tables.
- **New tables:** define `history/Tracked<Entity>.ts` with `defineTrackedEntity`, register it in `Setup.ts`, and add the table to `TRACKED_TABLES` in `eslint.config.js`. A table without history needs a reason in `UNTRACKED_TABLES` in `tests/unit/history.schema.test.ts`, and each tracked entity needs a fixture in `tests/integration/history.rights.http.test.ts`; both tests fail otherwise.
- **Rules:** `validate` checks the merged state without database access, before anything is written. `guard` gets the transaction and runs after the row and its lists are written; it only sees its own row, so keep it to rules of that row (e.g. "archived content cannot be modified"). Rules across rows (references, unique codes, variants against their species) belong to the content verification: a module registers `AssetsService.registerContentType({ assetType, verify })`, and the history calls the registered `ActionVerifier`s once at the end of every action, after all its writes and before the commit, with every touched row; the kernel verifies each asset whose content the action changed and that is not archived: created assets, changed status or rulesets, and rows whose `root` is the asset and that are part of its content (`contentOfRoot`, false for links and media). Renaming, tags, links, media and releases are not checked again. It stores all references first and checks afterwards, so every check sees the final state of all touched assets. So creating, changing rulesets, undoing, restoring and leaving `ARCHIVED` are all checked on the real final state, and no use case calls those checks itself. Everything runs for every change, including undoing and restoring; a rejection rolls back the whole action.
- **Lists of other modules:** a module can store a list per asset as a field of the asset with `AssetsService.registerTrackedList` and change it with `updateTrackedList`, like `tagIds`. It shares the version and the history rights of the asset: editors who assign tags also read and undo that history.
- **Fields:** every column is classified: `value`, `counter`, `position`, `list`, `account` and `secret` (no value is ever stored), or `ignore`. Fields that grant rights use `field.value({ revertible: false })`. Set the limit in the definition, otherwise `standard` applies.
- **Rights:** the history only exists for people who may change the content; seeing it is not enough. Everybody else gets 404. Who may change content is decided once, by `decideContentWrite` (`#core/content/writeAccess`): administrators everything, global content only them, campaign content owner and editors, restoring versions only the owner; `AssetsService.assertCanWrite(context, action, campaignId, db)` applies it to writes. `campaignHistoryAccess` derives the history rights of campaign content from the same rule (`editRoles` only for campaign settings); players only get rows through `ownedByPlayer`. The asset history additionally only lets the campaign undo archiving, restoring and the module actions listed as `revertibleActions` of the content type. System admins pass every check, but technical limits apply to them too. Rights use the role at access time and the campaign from the row, never from the client.
- **Behavior:** undoing and restoring are new entries, the history is never rewritten. Deleted rows stay deleted and their history is no longer readable. Archived content can be restored. Conflicts are detected per field through `baseVersion`, and `merged` reports values that were kept.
- **Deliberately direct:** `campaign_invitations` (nothing to restore), `media_files` (nobody can edit a file; the status only records the upload), the ruleset progression tables (never change), and for `users` the own profile and everything in `auth`, because that history only covers changes by administrators. For the same reason, `user.update` keeps a strict version check.

### Errors

Throw subclasses of `AppError` / the HTTP errors in `src/core/error/http/` (`NotFoundError`, `ForbiddenError`, `ConflictError`, `ValidationError`, ...). `registerErrorHandler` plus `errorMapper` turn them into the standard error payload. Modules add their own under `error/http/` when needed.

## Frontend

The frontend is rebuilt from the clickdummy (`clickdummy/`, local only; `cd clickdummy && npm run dev` → `http://localhost:5180/#/` with a screen overview). It is the reference for features, flows, theme and components; take its components over converted to TypeScript, not copied 1:1, and take data from props or the API instead of its `data/*.js`. Its admin screens (`views/admin/*`) are out of scope. Example content from the clickdummy (texts, the "Die Schatten von Elaria" campaign) may be used. The older screenshots in `example/UI/` are superseded by it.

### Structure

Target layout (built step by step, see the plan; today `styles/`, `core/api/`, `core/i18n/`, `locales/`, `layouts/`, `app/router.ts` and the scaffold pages exist):

### API and server data

- Types are generated from the backend's OpenAPI document: `npm run api:types` exports it without a database (`apps/backend/scripts/export-openapi.ts`, builds the app like the unit tests) and writes `src/core/api/generated/schema.d.ts` (committed, never edited). Run it after every backend route or DTO change; CI fails on a stale file. Recursive Zod schemas must be registered with a name (`z.globalRegistry.add(schema, { id })`, see `#core/rules/contracts`), and `z.json()` is never used directly but `jsonValueDto` from `#core/http/dto`; otherwise the document refers to schemas it doesn't contain.
- Requests go through `api` from `@/core/api/client` (openapi-fetch, paths with the `/api/v1` prefix) and `unwrap(...)`, which returns the data or throws an `ApiError` (`status`, `code` from the backend's error envelope, `details`, `requestId`, `retryAfterSeconds`; `NETWORK_ERROR`/`UNKNOWN_ERROR` without an envelope). The UI translates `code`, never shows `message`.
- A 401 renews the session once (`POST /auth/refresh`, shared by parallel requests) and repeats the request; auth routes are excluded. A failed renewal fires `onSessionExpired`, which clears the query cache.
- 412 (`isVersionConflict`, `versionConflictDetails`: `currentVersion` and the conflicting fields) is shown by the editor as "changed by someone else" with reload / keep my change.
- Server data lives in TanStack Vue Query, UI state in Pinia. Every query takes its cache rule from the one table `src/core/api/cachePolicy.ts` (`...cachePolicy("list")`: `static`, `content`, `list`, `live`, `private`, `signedUrl`) and its key from `globalKey`/`meKey`/`campaignKey` (`src/core/api/queryClient.ts`); modules set no `staleTime` of their own. Logout clears the whole cache, a role or membership change clears that campaign (`clearCampaignCache`). Failed requests are retried only for 5xx/network errors, mutations never.

### Languages

- **Texts never break the app.** A message that is missing or doesn't compile falls back to German; if German has none either, nothing is shown (the key in development, with a console warning). A language that doesn't load falls back to German, and without any messages the app still starts. Dates with an invalid value or time zone show nothing or use the browser's zone. Problems are caught before shipping by `i18n:check` (it also compiles every message), not at runtime.
- German and English from the start, more without rework. Text on screen comes only from message files: `src/locales/<lang>/<namespace>.json` (`common`, `errors`, `glossary`) and `src/modules/<module>/locales/<lang>.json` (namespace = module name). Keys name the meaning (`common.actions.save`, `locations.editor.save`), not the text. German is the reference; every change to it comes with English in the same change.
- Translate with `useAppI18n()` from `@/core/i18n` (`t(key)`, `t(key, named)`, `t(key, count, named)` for plurals); keys are typed against the German files (`src/core/i18n/generated/messages.d.ts`, `npm run i18n:types`), so a typo is a compile error. `$t` is not installed. Keys built at runtime are declared next to their use with a comment `// i18n-dynamic: errors.*`.
- `@intlify/vue-i18n/no-raw-text` refuses text in templates (only the old scaffold pages are exempt until they are replaced). Labels and toasts in scripts also go through `t()`.
- API errors are shown by code: `t(errorMessageKey(error))` (`errors.<code>`), never the server's `message`.
- D&D terms come from the glossary (`useGlossary().term("species", edition)`): one fixed wording per language, with overrides per ruleset edition (2014 "Volk"/"Race"). Term names are listed in `@dnd/i18n` (`GLOSSARY_TERMS`); `i18n:check` makes sure every language has them.
- Dates and numbers only through `useFormat()` (`date(value, "date" | "dateLong" | "dateTime" | "time")`, `number`, `relative`) in the active language and the user's time zone (`setTimeZone`, from the profile).
- Language choice: profile (`users.locale`, applied with `setLocale` after sign-in) → last choice in this browser → browser languages → German. No language in app URLs. Only the active language is downloaded (one chunk per file).
- Pseudo language: `?lang=qps` in development shows German with accents, 40 % longer and in brackets; text that stays plain is hard-coded, text that breaks is too tight.

Tests: Vitest + Vue Test Utils (`apps/frontend/tests/unit`, `npm run test:unit --workspace @dnd/frontend`; the root `test:unit` runs backend and frontend), Playwright for flows. `tests/unit/theme.test.ts` fails on raw color values outside `styles/main.css`.

### Theme

- **Tailwind 4**, configured in CSS: tokens are defined once in `@theme` in `src/styles/main.css` (`--color-*`, `--font-*`, `--radius-*`, `--shadow-*`, `--breakpoint-md`) and become utilities (`bg-navy-950`, `bg-parchment-card`, `text-ink-2`, `border-gold`, `rounded-card`, `shadow-soft`). There is no `tailwind.config.ts`.
- Components use only these semantic utilities, never raw hex/rgb values or arbitrary color values like `bg-[#7a1f2b]`. A missing color becomes a token. Material values that are no utilities (paper texture) are custom properties on `:root` in the same file.
- Custom CSS is fine where utilities aren't enough (parchment texture, ornamental frames, animations): in a layer of `main.css` (`.parchment`, `.frame-double`, `.card`, `.input`, `.btn-*`, `.badge`, `.table`) or a scoped component style, named by meaning, using the tokens.
- Look: dark navy sidebar and top bar, parchment work surface with a golden double frame and ornamental corners, burgundy primary color for actions and the active navigation, serif typography (Libre Baskerville for headings, Lora for text, self-hosted through `@fontsource`, no Google Fonts CDN), soft colored pill badges, table lists with filter bars and pagination.
- App assets live in `public/assets/`: the icon sprite `icons/chronik.svg` (names in `components/base/icon-names.json`) and `deko/` (frame corners, compass rose, seals, mountain motif). Example images of the clickdummy (characters, maps, monsters …) are no app assets.

### Conventions (from the clickdummy)

- **Page layout:** breadcrumb → domain icon + title → subtitle → primary action → search/filters → count/sort → content → pagination (`PageHeader`, `ListToolbar`, `ResultBar`, `DataTable`, `PaginationBar`).
- **Exactly one primary action per context** (burgundy); others are secondary. Labels name the concrete action ("Ort erstellen", "Monster speichern").
- **Buttons** only through `BaseButton` (variant, size lg/md/sm/xs, icon, `to`), icon-only buttons through `IconButton` (label required → aria-label + tooltip), closing through `CloseButton`. No raw `.btn` classes in views.
- **Icons** only through `<Icon name="…" />` from the sprite (`nav-*`, `aktion-*`, `orig-*`, `ui-*`), sizes 16/20/24/32, domain icons in page headers 40–48. Same function = same icon.
- **Forms:** labels outside the fields (`FormField`), errors directly at the field.
- **Editors** are child routes of the list (`…/neu`, `…/:id/bearbeiten`) in an `EditorDrawer` (drawer on desktop, editor page on mobile); every section has content. The list renders `<RouterView :key="$route.fullPath" />`.
- **Tabs with their own URL** through `TabNav` with `to`.
- **Single values** (character values, quantities, visibility, links …) change in the small value editor (`ValueEditor`, popover on desktop, bottom sheet on mobile); clickable values are wrapped in `EditableValue`.
- **Status** always through `StatusBadge` (tone + icon from one central mapping), visibility through `VisibilityLabel`. Same meaning = same badge tone.
- **Long texts** through `ExpandableText`. Server HTML only through `SafeHtml` (see above), mentions through `MentionText`.
- **Responsive** with the `md` breakpoint (768 px): reorder content on mobile, never a horizontal page scrollbar.
- **Rights in the UI** only hide what the API refuses anyway (create, release, settings only for the game master); the backend decides.
- **New building blocks:** check for a shared component first; module folders only for domain-specific parts.

## Optional local tooling: graphify

graphify is optional and runs only locally. If it is configured in a workspace (the `graphify` CLI and `graphify-out/graph.json` exist), use it as described in the `## graphify` section below. If not, ignore that section and work as usual. Nothing in the project may depend on it: the app, tests, CI and npm scripts must work without it.

- Build and update the graph only with `graphify update .`, which extracts locally from the code. Don't use the hosted graphify platform and don't configure API keys or external backends for it.
- The files graphify creates stay in the local workspace and are never committed: `graphify-out/`, `.claude/skills/`, `.claude/settings.json` and `.claude/CLAUDE.md`. They are excluded through `.git/info/exclude`, not `.gitignore`.
- To set it up in a checkout, add those exclusions, then run `graphify install --project`, `graphify claude install --project` and `graphify update .`.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
- A committed graphify-out/graph.json is rewritten whole on every build, so a large diff to it in a pull request is expected. Do not flag it as churn or suggest skipping the graph rebuild or its hooks.
